# 三份设计方向（固定入口内，等待选择）— R1

三份方向都满足同一业务口径：同一入口（桌面右下角小芽 → 右侧栏 / 独立工作区；手机全屏）、同一会话、同一权限与守门、同一记录 ID。差异集中在：**消息密度、核对位置、移动端布局**。不重开品牌，不改首页，全部复用 shadcn 原语与全局主题。

选稿方式：选 A / B / C 之一，或写明“以 X 为主 + Y 的某部分”。未选前不进入 UI1。

## 0. 共同遵守（三份都是）

1. 待确认卡有绑定对象；页面切换不静默改卡。 [C] 需求 Q5
2. 每张写操作卡都有：对象、内容摘要、影响说明、明确批准按钮；模型不能自批。 [C] 需求 §3.4-3.5
3. 批准前必须能看到**实际对象、关键事实、修改内容与附件关联**；`亮点 2 条` 之类的数量摘要不能代替完整批准内容（可折叠，但必须可展开核对）。
4. 回执只来自服务端事实；不确定只按原操作核对。 [C] 现有观察状态核对模式 `review-client.tsx:292-328`；通用操作回执 [A] 依赖 CONTRACT-R1
5. 图片：上传/分析/保存/归档分开反馈；分析失败可继续文字。 [C] 需求 §3.4
6. 批次逐项核对、逐条回执；单条问题不阻塞其余。 [C] 需求 Q7
7. 正式守门不变：raw_text 不改写、AI 草稿需教师确认、指南 ✓ 不由聊天点亮。 [C] 需求 §3.6-3.7
8. 手机：软键盘、安全区、返回、焦点、长卡片按 `brief.md` §2.4；核心目标 ≥44px、无横向滚动。
9. 小芽头像 24–32px、状态有文字；减少动态仍可理解。 [C] 需求 Q9
10. **长文规则**：短文本约束只作用于进度/工具摘要（如“正在整理…”）；一般教育回答、范围内查询、成长分析可以正常分段、展开来源、长文呈现，不裁断正文。 [R1]
11. **服务分层**：教育咨询、看图问答/作品分析、临时观察准备、已保存观察的正式整理是不同服务；看图问答不要求选幼儿、不要求 ≥10 字原文、不自动建观察（`brief.md` §1.1）。 [R1]

## 方向 A｜册页卡（Notebook Cards）— 低密度 · 卡内核对 · 单列卡流

**立场**：助手像翻观察册。一屏一个主题，卡片即正文，对话是卡片之间的短过渡；普通回答按“段落 + 来源”阅读式呈现。适合“记录→核对→归档”这条主线的安静气质。

### A.1 桌面右侧栏（示意，统一案例见 `synthetic-example.md`）

```
┌ 芽芽 · 与小满的观察         历史 · 工作区 · ✕ ┐
│ 芽芽：这条观察我整理好了，请你看卡核对。        │
│ ┌──────────────────────────────────────────┐ │
│ │ 观察草稿卡        草稿 · 小满 · 10月8日    │ │
│ │ 原文（保存后不可改）                        │ │
│ │ “小满自己搭长桥，中间塌了三次，他换了更宽的  │ │
│ │  底座，第四次搭稳了。”                      │ │
│ │ [图] 积木区 · 2 张缩略图（1 张共同）        │ │
│ │ AI 整理 · 科学  子领域：数学认知            │ │
│ │ 发展表现说明 / 发展亮点 / 支持建议（可展开）│ │
│ │ ┌ 核对区（展开）─────────────────────────┐ │ │
│ │ │ 对象 小满（中班·向日葵班）              │ │ │
│ │ │ 日期 10月8日 · 情境 积木区              │ │ │
│ │ │ 事实依据 与原文逐字对照 [查看对照]      │ │ │
│ │ │ 图片 积木区全景（与阿依共用）+ 长桥特写 │ │ │
│ │ └──────────────────────────────────────┘ │ │
│ │ [修改草稿]  [确认归档]（保存中→回执）      │ │
│ └──────────────────────────────────────────┘ │
│ 芽芽：归档后记录会进入成长档案。                │
│ ┌─ 输入 ────────────────────────────────────┐ │
│ │ [对象：小满] [来源：观察草稿]               │ │
│ │ 写下补充或新问题…                    📎 ↑ │ │
│ └──────────────────────────────────────────┘ │
└────────────────────────────────────────────────┘
```

### A.2 密度与结构

- 进度/工具摘要 ≤2 行；**普通回答不受 2 行限制**，按段落、列表与“展开来源”呈现，必要时整卡滚动。
- 卡片 = 完整业务单元（原文、草稿、核对区、动作、回执）；同一主题不拆成多条气泡。

### A.3 核对方式

- **卡内核对**：核对区默认折叠，卡片标题显示“待核对”；展开后是事实清单与逐字对照（对象/日期/事实/图片关联），批准内容完整可核对。
- 批准 = 卡片底部主按钮，按钮文案随内容变化；点击后按钮进入“保存中”，结果在原地变回执条。
- 多幼儿批次 = 多张同构卡纵向排列，每张卡自带复选框与“保存已选”，见 A.5。

### A.4 失败与回执

- 卡内状态条按 `recovery-spec.md` 六类分型：明确失败（可重试）/ 前提冲突（重新核对）/ 结果未知（按原操作核对）/ 执行中（保留锁，其他条目照常）/ 已保存详情暂不可读（只读详情）/ 批次分项。
- 不得把所有非成功状态统称“待核对”。

### A.5 批次（统一案例：小满、阿依，共 2 条）

```
│ ☑ 小满卡（已核对）  [保存此条]              │
│ ☐ 阿依卡（待补充：提醒的具体说法）[补一句]   │
│ [保存已选 1 条]   已保存 0 条 · 1 条待补充   │
```

- 未勾选不保存；待补充卡不阻塞其余；保存后卡片变只读回执，只对未完成且**可安全重试**的项出现操作。

### A.6 移动端 390（全屏）

```
┌──────────────────────────┐
│ ‹ 芽芽           历史 ⋯ │
│  ┌────────────────────┐  │
│  │ 观察草稿卡          │  │
│  │ …（整页纵向滚动）    │  │
│  │ [修改]  [确认归档]  │  │
│  └────────────────────┘  │
│  ┌── 输入（随键盘抬升）─┐ │
│  │ [对象：小满]         │ │
│  │ 写下补充…      📎 ↑ │ │
│  └────────────────────┘ │
└──────────────────────────┘
```

- 卡流单列；**卡片操作在卡内**（桌面与手机同一规则），只有输入区吸附底部安全区之上。核对表单同样随软键盘抬升。

### A.7 代价与适配

- 优点：最贴合“轻量成长观察册”；卡片自证业务边界，演示讲解顺序自然；长回答阅读体验好。
- 代价：卡片高，多卡批次滚动长；快速碎片问答的“对话感”弱。
- runtime 形态：消息可承载复杂自定义组件（工具卡）即可，无分栏状态源要求。

## 方向 B｜短句流（Thread Checkpoints）— 高密度 · 逐步核对 · 底部抽屉编辑

**立场**：助手像一位在旁边逐步确认的搭班老师。进度与检查点短；核对在专注抽屉里完成；知识性回答可展开成长段，不硬塞气泡。

### B.1 桌面右侧栏（示意）

```
┌ 芽芽 · 与小满的观察         历史 · 工作区 · ✕ ┐
│ 芽芽：收到，这次在积木区看到的？               │
│ 我：小满自己搭长桥，塌了三次换底座成功了。     │
│ 芽芽：好。要把它整理成观察草稿吗？             │
│       [整理成草稿]  [只保存原文]              │
│ 芽芽：整理好了：科学 · 数学认知。              │
│       [核对草稿]  草稿预览 2 行…              │
│ 我：（点核对草稿）                            │
│ ┌ 抽屉：核对草稿 ─────────────────────────┐  │
│ │ 对象 小满 · 10月8日 · 积木区             │  │
│ │ 原文对照 / 修改内容 / 附件关联            │  │
│ │ [保存修改并重新审核]  [确认归档]          │  │
│ └──────────────────────────────────────────┘  │
│ 芽芽：已归档。档案已更新。  回执 14:32 · #a1c1 │
│ ┌─ 输入 ────────────────────────────────────┐ │
│ │ [对象] [来源] 回复…                   📎 ↑ │
│ └──────────────────────────────────────────┘ │
```

- 关闭抽屉**不丢弃未提交编辑**：保留在草稿区并显示“有未提交修改 [继续编辑] [放弃修改]”；只有明确“放弃修改”才清理；再次批准仍需最新内容核对。

### B.2 密度与结构

- 进度、追问、确认是短气泡（≤3 行）；一般回答进入“回答块”，可多段、可展开来源，不裁断。
- 写操作拆成“准备 → 核对 → 回执”三段小消息，每段一个主按钮；编辑与逐字对照进 `Sheet`。

### B.3 核对方式

- **逐步核对**：每个检查点单独成消息，未核对完不进入下一步；批次内每条各自有检查点序列，单条疑问不升级为全批卡死。
- 批准按钮在抽屉底部，抽屉展示实际对象、关键事实、修改内容与附件关联。

### B.4 失败与回执

- 失败按六类分型，以系统小行替换对应步骤（“整理失败，输入还在 [重试]”），不打断整条时间线。
- 结果未知单独一条琥珀消息：“保存结果按原操作核对 [重新读取核对]”；执行中显示“此操作仍在进行中”，其他条目可继续。

### B.5 批次（统一案例 2 条）

- 每个幼儿一条子会话线程：`小满：已确认归档 ✓ / 阿依：待补充 [补一句]`。
- 顶部批次条：`本批 2 条 · 已保存 1 · 待补充 1`；分项状态按六类，点击跳转对应线程。不得把所有非成功项都拿去重发。

### B.6 移动端 390（全屏）

- 对话流占满；点“核对/补充”开**底部抽屉**（80–90% 视高，可全屏），软键盘抬升当前抽屉的输入与核对表单。
- 优先使用 `100dvh` 与 `env(safe-area-inset-*)`；仅当浏览器行为不足时才用 `visualViewport` 补偿，避免与抽屉自身抬升叠加成双重抬升。

```
┌──────────────────────────┐
│ ‹ 芽芽           历史 ⋯ │
│ 芽芽：…                  │
│ 我：…                    │
│ 芽芽：整理好了 [核对草稿] │
│ ┌─ 底部抽屉 ───────────┐ │
│ │ 核对草稿             │ │
│ │ 对象·日期·原文对照    │ │
│ │ [确认归档]           │ │
│ └──────────────────────┘ │
│ 输入…               📎 ↑ │
└──────────────────────────┘
```

### B.7 代价与适配

- 优点：每步小、心理负担低；演示时能逐句讲清“谁在确认什么”。
- 代价：消息条数多；长对话后回溯要找历史；抽屉频繁开关（未提交编辑保留规则要清楚）。
- runtime 形态：需要流式文本 + 自定义工具消息 + 侧/底抽屉；历史分页要求高。

## 方向 C｜核查台（Split Workbench）— 中密度 · 分栏核对 · 双标签页

**立场**：助手是带核对台的工作间。左侧对话负责“说”，右侧核查区负责“核”。**是否分栏取决于实际可用宽度**：只有独立工作区或实际内容区 ≥ 约 900px 时分栏；360–460px 的侧栏保持可读单列，核对动作以覆盖式面板进行，不把两列挤进窄栏。

### C.1 桌面独立工作区（示意）

```
┌ 芽芽工作区 ────────────────────────────────────────────────┐
│ 会话                │ 核查区（当前：小满 · 观察草稿）        │
│ 芽芽：整理好了。     │ ┌───────────────────────────────────┐ │
│ 我：把阿依也加上。   │ │ 原文（不可改）…                   │ │
│ 芽芽：已生成阿依卡。 │ │ 草稿 科学·数学认知 [可编辑]        │ │
│ [待核对 1]          │ │ 附件 积木区全景（与阿依共用）      │ │
│                     │ │ 核对：对象/日期/逐字对照/修改内容  │ │
│                     │ │ [确认归档] [稍后处理]              │ │
│                     │ └───────────────────────────────────┘ │
│                     │ 队列：☑小满 (已保存) ☐阿依(待补充)     │
│ ┌ 输入 ───────────┐ │ [保存已选 1 条]                       │
│ │ 回复…      📎 ↑ │ │                                       │
│ └─────────────────┘ │                                       │
└─────────────────────────────────────────────────────────────┘
```

- 侧栏（360–460px）不分栏：对话单列 + 点击后在侧栏内覆盖一级核查面板；批量核查引导到独立工作区。

### C.2 密度与结构

- 左侧进度与状态消息短；一般回答可在左侧或独立阅读列展开（分段 + 来源），不裁断。
- 右侧只显示事实与决定，不出现 AI 对话文本；一次一项 + 队列。

### C.3 核对方式

- **分栏核对**：聊天里的“核对/修改/批准”跳到右侧当前项；队列逐项切换；批准在右侧卡片底部。
- 侧栏则退化为覆盖式核查面板（同一内容、单列呈现）。

### C.4 失败与回执

- 结果按六类分型；左侧回执行承载结果，右侧载详情；执行中保留操作锁，队列其他项可继续。
- 结果未知时右侧变“按原操作核对”面板（只读核对），左侧同步黄条；不自动重发。

### C.5 批次（统一案例，独立工作区）

- 队列 = 批次主界面：勾选 + 逐项状态（已保存/明确失败/冲突/结果未知/待补充）+ “保存已选”；左侧只显示批次结果摘要。

### C.6 移动端 390（全屏）

- 顶部两个标签：**对话** ｜ **核对（1）**；角标为待核对条数（不是首页待办计数）。
- 点核对标签进入单列核对页；批准后自动回对话并出现回执行。
- 核对页的核对表单同样处理软键盘与安全区；输入区仅在对话标签抬升。

```
┌──────────────────────────┐
│ ‹ 芽芽      [对话][核对1]│
│ ┌ 核对（单列）─────────┐ │
│ │ 小满 · 观察草稿       │ │
│ │ 原文 / 草稿 / 附件    │ │
│ │ 核对清单              │ │
│ │ [确认归档]            │ │
│ │ 队列 ☑小满 ☐阿依     │ │
│ │ [保存已选 1 条]       │ │
│ └──────────────────────┘ │
└──────────────────────────┘
```

### C.7 代价与适配

- 优点：批量与桌面效率最高；与现有 Review 并列阅读一致。
- 代价：信息密度最高，需克制；窄侧栏降级与共享投影实现复杂。
- runtime 形态：会话与核查面板共享同一消息/卡片投影，避免第二状态源（TECH0 评估）。

## 对比与选择提示

| 维度 | A 册页卡 | B 短句流 | C 核查台 |
|---|---|---|---|
| 消息密度 | 低（卡=正文；长答可展开） | 高（进度短消息+回答块） | 中（短状态+侧栏详情） |
| 核对位置 | 卡内展开 | 抽屉逐步 | 分栏/覆盖面板 |
| 批次 | 卡列表 | 子线程 + 批次条 | 队列面板（独立工作区） |
| 移动端 | 单列卡流 | 对话 + 底部抽屉 | 对话/核对双标签 |
| 演示讲解 | 最直观 | 最细致 | 最完整 |
| 长文问答 | 好 | 中（回答块） | 好 |
| 长对话回溯 | 中 | 弱 | 强 |
| 实现复杂度 | 低 | 中 | 高（分栏需宽度条件） |
| 与现有 Review 一致度 | 中 | 低 | 高 |

选择时可能考虑（[A]，非定论）：若比赛演示首选“清楚讲完一条观察”，A 或 B；若重点展示“一批多幼儿不串档”，C 的独立工作区；若兼顾日常速记，B。

## 推荐组合（主评审建议，待出图评审；不是用户已批准的设计图）

- **A 作为默认自然对话与卡片体验**（侧栏 / 手机 / 工作区）；
- **C 的批量核查只用于独立工作区**（达到可用宽度才分栏），侧栏不强行分栏；
- B 保留为备选，不叠加进组合，避免第三套交互隐喻。

状态：A / B / C 均**未选**；组合建议只影响待出图稿的评审顺序，不改变“用户选稿后才进入 UI1”。

## 若想合成

允许的选择方式：例如“A 的对话与卡内核对 + C 的独立工作区批量队列”、“A 的移动端 + B 的桌面抽屉”。合成稿由设计侧补差异说明后再交 UI1；不新造整站第四套风格，不重开品牌。
