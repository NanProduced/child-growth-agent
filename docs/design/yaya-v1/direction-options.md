# 三份设计方向（固定入口内，等待选择）

三份方向都满足同一业务口径：同一入口（桌面右下角小芽 → 右侧栏 / 独立工作区；手机全屏）、同一会话、同一权限与守门、同一记录 ID。差异集中在：**消息密度、核对位置、移动端布局**。不重开品牌，不改首页，全部复用 shadcn 原语与全局主题。

选稿方式：选 A / B / C 之一，或写明“以 X 为主 + Y 的某部分”。未选前不进入 UI1。

## 0. 共同遵守（三份都是）

1. 待确认卡有绑定对象；页面切换不静默改卡。 [C] 需求 Q5
2. 每张写操作卡都有：对象、内容摘要、影响说明、明确批准按钮；模型不能自批。 [C] 需求 §3.4-3.5
3. 回执只来自服务端事实；不确定只“重新读取原回执”。 [C] `review-client.tsx:292-328`
4. 图片：上传/分析/保存/归档分开反馈；分析失败可继续文字。 [C] 需求 §3.4
5. 批次逐条核对、逐条回执；单条问题不阻塞其余。 [C] 需求 Q7
6. 正式守门不变：raw_text 不改写、AI 草稿需教师确认、指南 ✓ 不由聊天点亮。 [C] 需求 §3.6-3.7
7. 手机：软键盘、安全区、返回、焦点、长卡片按 `brief.md` §2.4；核心目标 ≥44px、无横向滚动。
8. 小芽头像 24–32px、状态有文字；减少动态仍可理解。 [C] 需求 Q9

## 方向 A｜册页卡（Notebook Cards）— 低密度 · 卡内核对 · 单列卡流

**立场**：助手像翻观察册。一屏一个主题，卡片即正文，对话是卡片之间的短过渡。适合“记录→核对→归档”这条主线的安静气质。

### A.1 桌面右侧栏（示意）

```
┌ 芽芽 · 与小满的观察         历史 · 工作区 · ✕ ┐
│ 芽芽：这条观察我整理好了，请你看卡核对。        │
│ ┌──────────────────────────────────────────┐ │
│ │ 观察草稿卡        草稿 · 小满 · 4月2日     │ │
│ │ 原文（保存后不可改）                        │ │
│ │ “……糖糖抱着布娃娃，先给它盖好小毯子……”      │ │
│ │ [图] 娃娃家 · 3 张缩略图                    │ │
│ │ AI 整理 · 社会  子领域：同伴交往            │ │
│ │ 发展亮点 2 条 / 支持建议 2 条 / 金句 1 条   │ │
│ │ ┌ 核对区（展开）─────────────────────────┐ │ │
│ │ │ 对象 小满（芽芽班）        来自档案页  │ │ │
│ │ │ 日期 4月2日 · 情境 娃娃家            │ │ │
│ │ │ 事实依据 与原文逐字对照 [查看对照]    │ │ │
│ │ │ 图片 3 张 · 仅作素材                 │ │ │
│ │ └──────────────────────────────────────┘ │ │
│ │ [修改草稿]  [确认归档]（保存中→回执）      │ │
│ └──────────────────────────────────────────┘ │
│ 芽芽：归档后记录会进入成长档案。                │
│ ┌─ 输入 ────────────────────────────────────┐ │
│ │ [对象：小满] [来源：观察草稿]               │ │
│ │ 写下补充或新问题…                    📎 ↑ │ │
│ └──────────────────────────────────────────┘ │
└────────────────────────────────────────────────┘
```

### A.2 密度与结构

- Yaya 文本 ≤2 行；卡片之间只允许一条过渡语；同一主题不拆成多条气泡。
- 卡片 = 完整业务单元（原文、草稿、核对区、动作、回执）。
- 普通问答以“短段 + 可选来源行”展示，不使用聊天气泡外观。

### A.3 核对方式

- **卡内核对**：核对区默认折叠，卡片标题显示“待核对”；展开后是事实清单（对象/日期/事实对照/图片），不是勾选框堆叠。
- 批准 = 卡片底部主按钮，按钮文案随内容变化（如“确认归档”）；点击后按钮进入“保存中”，结果在原地变回执条。
- 多人批次 = 多张同构卡纵向排列，每张卡自带复选框与“保存已选”，见 A.5。

### A.4 失败与回执

- 卡内错误条（`Alert` 语义）：缺信息=中性提示；权限=原因 + 下一步；模型失败=保留输入 + 重试；不确定=“待核对卡”替换动作区，只提供“重新读取核对”。

### A.5 批次

```
│ ☑ 小满卡（已核对）  [保存此条]              │
│ ☑ 阿依卡（已核对）  [保存此条]              │
│ ☐ 小北卡（待补充：成人帮忙方式）[补一句]     │
│ [保存已选 2 条]   已保存 1 条 · 1 条待核对  │
```

- 未勾选不保存；待补充卡不阻塞其余；保存后卡片变只读回执，只对未完成项出现操作。

### A.6 移动端 390（全屏）

```
┌──────────────────────────┐
│ ‹ 芽芽           历史 ⋯ │
│  ┌────────────────────┐  │
│  │ 观察草稿卡          │  │
│  │ …（整页纵向滚动）    │  │
│  │ [修改]  [确认归档]  │  │
│  └────────────────────┘  │
│  ┌── 输入（随键盘抬升）─┐ │
│  │ [对象：小满]         │ │
│  │ 写下补充…      📎 ↑ │ │
│  └────────────────────┘ │
└──────────────────────────┘
```

- 卡流单列，无吸底操作条（卡片操作在卡内）；输入区吸附底部安全区之上。

### A.7 代价与适配

- 优点：最贴合“轻量成长观察册”；卡片自证业务边界，演示讲解顺序自然。
- 代价：卡片高，多卡批次滚动长；快速问答的“对话感”弱。
- runtime 形态：消息可承载复杂自定义组件（工具卡）即可，无分栏状态源要求。

## 方向 B｜短句流（Thread Checkpoints）— 高密度 · 逐步核对 · 底部抽屉编辑

**立场**：助手像一位在旁边逐步确认的搭班老师。每次只问一件事，检查点短，核对在专注抽屉里完成。适合“边带班边记”的碎片输入。

### B.1 桌面右侧栏（示意）

```
┌ 芽芽 · 与小满的观察         历史 · 工作区 · ✕ ┐
│ 芽芽：收到，这次在娃娃家看到的？               │
│ 我：糖糖抱娃娃，给娃娃盖毯子，还叫小雨当姐姐。 │
│ 芽芽：好。要把它整理成观察草稿吗？             │
│       [整理成草稿]  [只保存原文]              │
│ 芽芽：整理好了：社会 · 同伴交往。              │
│       [核对草稿]  草稿预览 2 行…              │
│ 我：（点核对草稿）                            │
│ ┌ 抽屉：核对草稿 ─────────────────────────┐  │
│ │ 对象 小满 · 日期 4月2日 · 原文对照       │  │
│ │ 领域/亮点/建议 可改                       │  │
│ │ [保存修改并重新审核]  [确认归档]          │  │
│ └──────────────────────────────────────────┘  │
│ 芽芽：已归档。档案已更新。  回执 14:32 · #a1c1 │
│ ┌─ 输入 ────────────────────────────────────┐ │
│ │ [对象] [来源] 回复…                   📎 ↑ │
│ └──────────────────────────────────────────┘ │
```

### B.2 密度与结构

- 用户与芽芽都用短气泡（≤3 行）；每张写操作卡拆成“准备 → 核对 → 回执”三段小消息，每段一个主按钮。
- 卡片只以紧凑预览出现（标题 + 2 行 + 动作），编辑与逐字对照进 `Sheet`（桌面右侧或居中抽屉）。

### B.3 核对方式

- **逐步核对**：每个检查点单独成消息，未核对完不进入下一步；但这只是引导，不是把一条疑问升级为全批卡死——批次内每条各自有检查点序列。
- 批准按钮放在抽屉底部，抽屉内容 = 最终核对区；关掉抽屉等于放弃本次修改（草稿仍在）。

### B.4 失败与回执

- 失败以系统小行替换对应步骤（“整理失败，输入还在 [重试]”），不打断整条时间线。
- 不确定回执单独一条琥珀消息：“保存结果待核对 [重新读取核对]”。

### B.5 批次

- 每个幼儿一条子会话线程（缩进或轻分隔）：`小满：已保存 ✓ / 阿依：待补充 [补一句] / 小北：未开始`。
- 顶部批次条：`本批 3 条 · 已保存 1 · 待核对 1 · 待补充 1`，点击可跳转对应线程。

### B.6 移动端 390（全屏）

- 对话流占满；点“核对/补充”开**底部抽屉**（80–90% 视高，可全屏），软键盘只抬升当前抽屉输入。
- 抽屉关闭 = 返回对话原位置；焦点归还触发气泡。

```
┌──────────────────────────┐
│ ‹ 芽芽           历史 ⋯ │
│ 芽芽：…                  │
│ 我：…                    │
│ 芽芽：整理好了 [核对草稿] │
│ ┌─ 底部抽屉 ───────────┐ │
│ │ 核对草稿             │ │
│ │ 对象·日期·原文对照    │ │
│ │ [确认归档]           │ │
│ └──────────────────────┘ │
│ 输入…               📎 ↑ │
└──────────────────────────┘
```

### B.7 代价与适配

- 优点：每步小、心理负担低；演示时能逐句讲清“谁在确认什么”。
- 代价：消息条数多；长对话后回溯要找历史；抽屉频繁开关。
- runtime 形态：需要顺畅的流式文本 + 自定义工具消息 + 侧/底抽屉；历史分页要求高。

## 方向 C｜核查台（Split Workbench）— 中密度 · 分栏核对 · 双标签页

**立场**：助手是带核对台的工作间。左侧对话负责“说”，右侧核查区负责“核”，互不挤压。适合批量与桌面效率，也最接近现有 Review 页的并列阅读。

### C.1 桌面（工作区/宽侧栏，示意）

```
┌ 芽芽工作区 ────────────────────────────────────────────────┐
│ 会话                │ 核查区（当前：小满 · 观察草稿）        │
│ 芽芽：整理好了。     │ ┌───────────────────────────────────┐ │
│ 我：把阿依也加上。   │ │ 原文（不可改）…                   │ │
│ 芽芽：已生成阿依卡。 │ │ 草稿 社会·同伴交往  [可编辑]       │ │
│ [待核对 2]          │ │ 图片 3 张 · 仅素材                 │ │
│                     │ │ 核对：对象/日期/事实对照           │ │
│                     │ │ [确认归档] [稍后处理]              │ │
│                     │ └───────────────────────────────────┘ │
│                     │ 队列：☑小满 ☑阿依 ☐小北(待补充)       │
│ ┌ 输入 ───────────┐ │ [保存已选 2 条]                       │
│ │ 回复…      📎 ↑ │ │                                       │
│ └─────────────────┘ │                                       │
└─────────────────────────────────────────────────────────────┘
```

- 宽侧栏（≥1440px）或独立工作区使用分栏；窄桌面侧栏（1024–1439px）退化为“对话 + 点击后覆盖式核查面板”。

### C.2 密度与结构

- 左侧消息短（≤2 行）+ 锚点链接（“在核查区打开”）；右侧一次只显示一张卡的完整核对内容 + 队列。
- 右侧核查区不出现 AI 对话文本；它是事实与决定区。

### C.3 核对方式

- **分栏核对**：聊天里所有“核对/修改/批准”动作都跳到右侧当前项；队列逐项切换。
- 批准仍在右侧卡片底部；左侧只出现回执行（“已归档 · 14:32 · #a1c1”）。

### C.4 失败与回执

- 左侧回执行承载结果；右侧载详情。错误按类别留在对应侧：数据/权限错误在右侧事实区，模型失败在左侧对话流。
- 不确定时右侧变“待核对”面板（只读回执核对），左侧同步黄条。

### C.5 批次

- 右侧队列天然承载批次：勾选 + 逐条状态 + “保存已选”；左侧只显示批次摘要与结果。

### C.6 移动端 390（全屏）

- 顶部两个标签：**对话** ｜ **核对（2）**；角标是待核对条数，不是任何首页待办计数的合并。
- 点核对标签进入单列核对页（同桌面右栏内容）；批准后自动回对话并出现回执行。
- 软键盘：仅在对话标签的输入区抬升。

```
┌──────────────────────────┐
│ ‹ 芽芽      [对话][核对2]│
│ ┌ 核对（单列）─────────┐ │
│ │ 小满 · 观察草稿       │ │
│ │ 原文 / 草稿 / 图片    │ │
│ │ 核对清单              │ │
│ │ [确认归档]            │ │
│ │ 队列 ☑小满 ☑阿依 ☐小北│ │
│ │ [保存已选 2 条]       │ │
│ └──────────────────────┘ │
└──────────────────────────┘
```

### C.7 代价与适配

- 优点：批量与桌面效率最高；与现有 Review 并列阅读一致；对话与事实职责清晰。
- 代价：信息密度最高，需要克制（安静表面规则）；窄桌面降级与窄侧栏实现更复杂。
- runtime 形态：需要会话状态与核查面板共享同一消息/卡片投影，避免第二状态源（TECH0 需评估 ExternalStore 投影或单 store 方案）。

## 对比与选择提示

| 维度 | A 册页卡 | B 短句流 | C 核查台 |
|---|---|---|---|
| 消息密度 | 低（卡=正文） | 高（逐步小消息） | 中（短消息+侧栏详情） |
| 核对位置 | 卡内展开 | 抽屉逐步 | 专用分栏/标签页 |
| 批次 | 卡列表 | 子线程 + 批次条 | 队列面板 |
| 移动端 | 单列卡流 | 对话 + 底部抽屉 | 对话/核对双标签 |
| 演示讲解 | 最直观 | 最细致 | 最完整 |
| 长对话回溯 | 中 | 弱 | 强 |
| 实现复杂度 | 低 | 中 | 高 |
| 与现有 Review 一致度 | 中 | 低 | 高 |

选择时可能考虑（[A]，非定论）：若比赛演示首选“清楚讲完一条观察”，A 或 B；若重点展示“一批多幼儿不串档”，C；若兼顾日常速记，B。

允许的选择方式：例如“B 的对话 + C 的桌面核查栏”、“A 的移动端卡流 + B 的桌面抽屉”。合成仍受同一业务口径与 `brief.md` 约束；合成稿由设计侧补一份差异说明后再交 UI1。
