# 失败恢复规格（只认原操作）— R2

原则（先于一切组件）：

1. **六类分开**：明确失败 / 前提冲突 / 结果未知 / 执行中 / 已提交详情暂不可读 / 批次分项。禁止把非成功统称“待核对”或“失败”。 [R1]
2. **成功 = 原操作成功 + 身份/内容/业务结果核对一致**。三者任一不满足都不是“已保存”。 [R2]
3. **结果未知只查询原 operation_id**：不允许“重新建提案/重新发起”绕过核验；不因当前业务状态未变就判定失败。 [R2]（通用 operation 身份 [A] 依赖 CONTRACT-R1；现有实现只有观察状态核对子集 [C] `review-client.tsx:292-328`）
4. **别人的写入不是你的成功**：另一端/另一位教师归档了不同内容时，不得显示“你的修改已保存”；要重新核对并重新批准自己的内容。 [R2]
5. **用户资产不丢**：输入文字、已选图片、已核对选择、未提交编辑在失败/关闭/切页后保留；只有服务端确认或用户明确放弃才清理。准备内容与聊天可按契约进行**账号私有持久化**（见 §1.9）。 [R2]
6. **恢复不自动重做写入**：刷新、重开、切设备、恢复旧对话都不自动执行旧操作。 [C] 需求 Q8、§5
7. **每一层分开反馈**：上传 / 准备 / 审核 / 保存 / 归档各自有状态；**中间效果不能冒充整条归档成功**。 [R2]
8. **守门不降级**：失败恢复不跳过确认、指南依据、成人帮助或版本复核；不自行提高成人帮助门槛。 [R2]

## 0. 证据范围（重要）

- 现有 Review 的“重新读取核对”读的是**观察业务状态**（`GET /api/observations?child_id=…` 后判断是否 `confirmed`），不是通用的 `operation_id` 回执账本。 [C] `review-client.tsx:292-328`
- 因此现有实现**无法区分**“原操作仍在进行中”“请求已发送但未落地”“请求未发送”，也**无法证明某次归档是你这次修改的结果**（可能是别人写的）。
- 通用操作身份、进行中查询与原操作回执查询依赖 **CONTRACT-R1**；字段名与接口待统一，最终命名交 YAYA0。UI 不自定义恢复算法，不自行生成操作 ID。以下场景中凡涉及通用 operation 的均为 **[A]/依赖项**，不是现状 [C]。

## 1. 场景与处理

### 1.1 明确失败且确认无已提交效果

- 检测：服务端明确拒绝且可证明未发生写入（如校验失败、400、无需重试的权限拒绝）。
- 表现：`没有完成，<原因>；输入还在。 [重试]`（权限类走 §1.7）。
- 动作：保留输入与选择；重试是显式点击；重试复用同一意图与原操作标记（不产生重复记录、不绕开核验）。

### 1.2 前提/版本冲突（409）

- 检测：409（班级资料变化、依据失效、目录版本不一致、归属变化、另一端已写入）。
- 表现：`前提已变化，需要重新核对` + 简短原因；旧批准/旧决定不沿用。 [C] `review-client.tsx:440-455`、`new-observation-client.tsx:279-283`
- **另一端归档了不同内容**：界面必须说明“当前记录已被另一操作更新为不同内容”，展示服务端事实，**不得显示“你的修改已保存”**；教师基于新事实重新核对 → 重新批准（或保留自己的新提案，走一次新的批准，而不是沿用旧批准）。 [R2]
- 禁止：沿用旧内容提交；覆盖对方；把冲突显示成自己的成功。

### 1.3 结果未知（含回执缺失、读取失败）

- 触发：网络中断；响应到达但无法证明结果；回执缺字段（缺操作引用/结果/身份）；核对读取失败。
- 表现：`保存结果未知，按原操作核对 [重新读取核对]` + `不会自动重复提交，也不会重新发起新提案。`
- 动作：**只查询原 operation_id**（当前实现只能查观察状态，通用回执待 CONTRACT-R1）：
  - 原操作成功 **且** 操作者身份、提交内容、业务结果三者核对一致 → 完成态；
  - 原操作成功，但业务结果与自己的内容不一致（另一操作写了不同内容）→ 按 §1.2 处理，不算自己的成功；
  - 原操作仍在进行中 → 保持执行中（§1.4），保留操作锁；
  - 回执缺失 / 读取失败 / 查不到 → 保持“结果未知”，不判失败、不重发、不新建提案；
  - 原操作已结束且确认无提交效果 → 保留输入可重试（§1.1）。
- 禁止：因当前业务状态未变就认为请求失败；用“重新建提案”绕过核验；自动重发；把“读到已归档”直接显示成“你的修改已保存”。 [R2]

### 1.4 原操作仍进行中

- 表现：`此操作仍在进行中` + 操作锁；其他无关问答、其他卡片、其他批次项可继续。
- 动作：保留对应操作锁与原操作标记；完成后再按回执落态；期间不提供重复提交按钮，也不允许新建替代提案。
- 禁止：锁住整个会话；把“进行中”显示为失败让教师重发。 [R1]

### 1.5 已提交，但详情暂时读不到

- 检测：原操作回执确认业务完成，详情读失败。
- 表现：`已提交，详情暂不可读，正在重新读取。请勿重复提交。` [C] `review-client.tsx:497-507、758-762`
- 动作：只读重试详情；已完成分支（档案更新/关联写入）按回执如实显示；不重新写。
- 注意：此状态仍需满足 §1.3 的“原操作成功 + 一致”前提，不能把别人写入的详情当成自己的结果。

### 1.6 批次部分结果

- 每项独立落入六类：已保存 / 明确失败 / 冲突 / 结果未知 / 待补充 / 未开始。
- 批次条：`本批 2 条 · 已保存 1 · 待补充 1`。
- 动作：**只对“明确失败且无提交效果”项重试**；冲突项重新核对；未知项按原操作核对；已保存项只读。`只处理未完成项` 不是“把所有非成功项一起重发”。 [R1]
- 禁止：因一条失败重发整批；把已保存项再次提交；跳过守门重试。

### 1.7 权限与身份状态

- 撤权/转班但账号有效：可一般幼教问答；业务对象按 403/范围说明，不渲染旧范围数据。 [R1]
- 账号停用、会话失效、身份服务不可用：**全部模型调用关闭（含一般问答）**，只保留登录/重试说明。 [R1]
- 范围变化（同账号）与换账号分开：
  - 范围变化：相关业务来源（历史、卡片、附件、待办）按新范围重新投影；聊天中受限内容显示受限投影。
  - 换账号：立即清空前一人的草稿、图片、消息、待提交选择，不闪现。 [C] `review-client.tsx:236-263`；`client.ts:77`
- 迟到写入被服务端拒绝（转班/停用/撤权后）。 [C] `access.ts:195-222`

### 1.8 基础设施不可用

- 身份 503：fail closed，隐藏模型与写入口。 [C] `write-access.ts:27-29`
- 数据库读失败：`读取暂未完成，请稍后重新读取；这不代表没有数据。` [C] `children/[id]/page.tsx:176、212`
- 计数未知（null）与真实零（0）分开；模型超时保留输入。 [C] `llm.ts:375-379`

### 1.9 关闭、取消与私人持久化

- **私人持久化**：聊天、私人草稿、已选素材/缩略图按契约做**账号私有持久化**；“准备态不自动写库”的准确含义是**不自动形成业务观察或正式确认记录**，不是关闭聊天就必然丢失准备内容。 [R2]
- 关闭侧栏/切页/停止模型显示：不撤销已完成写入；**后台已保存或已开始执行的操作不得显示成已撤销**，继续按原操作核对。 [R1]
- 关闭 B 抽屉：保留未提交编辑，显示 `有未提交修改 [继续编辑] [放弃修改]`；只有明确“放弃修改”才清理。
- 取消上传/分析：停止该任务，保留原图与文字。
- 删除会话：只删会话/消息与私有草稿；正式观察、已归档关联与仍被引用的图片保留；不按目录前缀清空。 [C] 需求 §5
- runtime 若因新消息取消旧 tool part：业务草稿独立于 tool part，不随之丢失；显式继续需当前身份、最新前提与新批准（映射依 TECH0/CONTRACT）。 [R1]

### 1.10 中间效果不等于整条成功

- 上传成功 ≠ 已保存；分析完成 ≠ 已归档；准备卡生成 ≠ 观察已创建；审核通过 ≠ 已归档。
- 回执必须按层展示（`message-spec.md` §3.8）；只有整条归档的完整回执（原操作成功 + 身份/内容/业务结果一致）才能显示 `已确认归档`。 [R2]
- 禁止用某一层的成功文案覆盖整条链路的未知/冲突状态。

## 2. 正反流程表（恢复语义）

| # | 场景 | 反例（错误处理） | 正确处理 |
|---|---|---|---|
| 1 | 原请求未结束，此时读到“未归档” | 判定失败并让教师重发 | 保持“执行中/结果未知”，按原操作核对，不重发 |
| 2 | 回执缺项（缺操作引用/结果/身份） | 当作成功显示 | 不显示成功；按“结果未知”等待完整回执 |
| 3 | 另一端已写入不同内容 | 覆盖对方或忽略冲突 | 409 → 读新前提 → 重新核对/批准 |
| 4 | 另一端归档了不同内容 | 显示“你的修改已保存” | 明确“记录已被另一操作更新为不同内容”；自己的内容走新批准 |
| 5 | 结果未知 | 重新建提案/重新发起绕过核验 | 只查原 operation_id；未结束就等待/核对 |
| 6 | 批准后教师又改了字段 | 沿用旧批准提交 | 旧批准失效，回核对并重新批准 |
| 7 | 恢复旧会话/换设备见到旧批准 | 自动执行 | 需当前身份 + 最新前提 + 新批准 |
| 8 | 批次 1 条失败 | 整批重发（含已保存） | 逐项分型，只重试“明确失败无效果”项 |
| 9 | 撤权后打开旧会话 | 继续渲染旧数据 | 受限投影；一般问答按角色能力；写操作拒绝 |
| 10 | 账号停用后仍可提问 | 仍调用模型回答 | 全部模型调用关闭 |
| 11 | 上传/准备/审核完成 | 显示“已确认归档” | 按层展示；整条完成才显示归档 |

[注] #1–#5 依赖通用操作身份/回执（[A] CONTRACT-R1）；现有实现只覆盖观察状态核对的子集 [C]，无法证明归属与一致性。

## 3. 图片管线状态机（分开反馈）

```
选择图片
  │
  ▼
待上传 ──上传失败──▶ 上传失败 [重试/移除]
  │
  ▼
已上传 ──分析失败──▶ 分析失败 [重试/继续文字]
  │
  ▼
分析完成（AI 解读，标注来源；不写入观察事实）
  │
  ▼
随记录保存 ──保存失败（明确）──▶ 可重试
            结果为未知 ─────────▶ 按原操作核对（不新建提案）
  │
  ▼
归档后随记录回看（对象引用；签名 URL 过期则刷新缩略图）
```

- 共同照片是**同一媒体对象的多个引用**；不复制文件、不复制事实。 [A] 引用模型归 MEDIA1
- 上传/分析状态可账号私有持久化；它们不构成业务观察，也不代表已归档。 [R2]

## 4. 幂等与防重复

- 主按钮点击即禁用 + `正在保存…`；完成前不恢复。
- 同一操作进行中不提供第二次提交；失败恢复后的再次提交是显式动作。
- 双击、迟到响应、旧请求代次不覆盖新状态：沿用现有 lookupKey/generation/ref 模式。 [C] `new-observation-client.tsx:101-106、181-212`、`teacher-provider.tsx:24-33`
